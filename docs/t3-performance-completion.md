# MonoCode performance implementation disposition — 2026-10-08

This document records the implementation against the [architecture review](t3-performance-review.md) and all 52 entries in the [T3 commit review](t3-performance-commit-review.md). MonoCode's comparison baseline is `188da0a03138ac37d24e8660859604f428f44e58`; T3's reviewed source is pinned to `300f7f9d45ff19c01bc987dbf1c3bc3e9a3a59ee`. Earlier highlighting, sidebar, explorer and transcript-pool improvements already belong to the MonoCode baseline. They are distinguished below from this implementation's changes.

The implementation uses MonoCode's existing Rust/Tauri, React, SQLite, Streamdown and provider interfaces. It does not replace those with T3's Electron or Effect stack. A disposition of **implemented** means the relevant mechanism has a MonoCode implementation; it does not mean the T3 patch was copied verbatim. **Equivalent already present** identifies code that already avoids the reviewed work. **Not applicable** identifies a concrete missing subsystem or a different existing contract. Specific remaining differences are recorded rather than called complete.

The implementation passed integrated review and validation. None of the measurements below establishes that the whole application is faster, uses less resident memory, or consumes less energy.

## Host format upgrade, backup and rollback

`host/store.ts` reads SQLite `PRAGMA user_version` before changing schema. Version 0 represents legacy inline snapshots; version 1 permits normalized metadata plus `session_blocks`. The version-1 marker commits in the same transaction as the first normalized write. A failed transaction restores the prior marker and data. An unknown newer version is rejected before index/schema changes. The tests cover all three cases.

The new host can read old inline snapshots, and old desktop clients still use the existing unprojected sync contract. An older released **host binary** cannot reconstruct normalized snapshots and did not historically check this new version marker. Binary downgrade therefore requires a pre-upgrade database backup; resetting `user_version` to 0 is not a conversion.

The default state directory is `~/.monocode-host`, overridden by `--data-dir` in `host/cli.ts`. The database is `<data-dir>/host.db`; attachments are its sibling `attachments` directory. Environment identity and paired-device hashes are in the database. Installed Unix launchers live at `~/.monocode-host/bin/monocode-host`; source-checkout management uses `node build/host/monocode-host.mjs`.

Before an authorized upgrade:

1. Stop the manually started host, or run `service uninstall --data-dir <actual-directory>` for a managed service so it cannot restart during backup. The service-uninstall path keeps data. Confirm the process is stopped and `running.json` has disappeared.
2. Copy the **entire** state directory to a new private backup directory. This preserves the database and any SQLite WAL/SHM sidecars, attachments and identity/device state. Do not copy only `host.db` while its writer is running, and do not print credential-bearing state files.
3. Record which host binary/version belongs to that backup. If a later downgrade is needed, stop/uninstall the new service, retain its current directory separately, restore the pre-upgrade directory, then run a compatible older binary.

No remote host deployment, remote backup, rollback or credential export was performed in this implementation task.

The real Brave fixture at `scripts/performance-preview.html` exercised 2,000 turns: middle-thread navigation, ordinary wheel scrolling, native word/cross-turn selection and exact copy, actual offscreen unmount/revisit with both tool-group and native Markdown disclosure choices, older-page insertion, and pinned live output. Recorded prepend arrival position stayed **108px → 108px** while 20 older turns were inserted; pinned output's bottom gap stayed **0px → 0px**. Wheel scrolling advanced the visible full rows while retaining only 16 rendered message rows in that view. These are functional browser checks, not timed whole-app benchmarks. Explicit select-all/Shift range selection can temporarily render the loaded eligible history and is deliberately more expensive than ordinary selection. Existing React `act(...)` warnings in a timer-based remote test are not silently converted into performance findings.

Remaining limitations are specific: full ordinary local settled-session serialization; every incremental code-line/selection case beyond the completion identity regression; normal-turn/single-item budget exceptions; 1,000-result remote search; legacy inline histories becoming normalized on their next durable write; and whole-process production tracing. Browser/native integration may find further corrections. These are not evidence for a framework replacement, copied cloud/mobile features, or an unqualified whole-app performance claim.
